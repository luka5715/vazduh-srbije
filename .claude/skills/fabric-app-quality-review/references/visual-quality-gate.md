# Visual fitness for the brief

Use this review for a new modern/premium experience, when the user says the result looks basic, or whenever the brief or design contract contains explicit visual requirements (references, effects, identity). Apply it to a maintenance change only for the rows the change touches. Review the actual rendered artifact, the visual contract and the latest feedback. Aesthetic judgment is contextual; tie each conclusion to the brief and visible evidence. Do not turn taste into a fake objective score. When a filled design contract exists, review its acceptance rows and record Meets brief / Needs revision / Untested per row. When none exists, derive two to four acceptance rows from the brief and the latest feedback, judge each with the relevant criteria of the table below, and say they are inferred.

| Criterion | Evidence to inspect | Revision trigger |
| --- | --- | --- |
| Composition | Initial desktop view and main user question | Most regions have equal visual weight; generic card grid obscures the decision |
| Identity | Selected reference principles, typography and component treatment | Only the palette, corner radii, shadows or animation distinguish the result from a default card grid or from the previous revision |
| Chart craft | Actual scales, labels, comparisons and marks | Decoration fills space; comparisons are hard to read; near-identical marks add no useful information |
| Typography | Rendered body, statuses, links and chart labels at actual scale; for a web frontend count visible text nodes by computed size per viewport (ignore aria-hidden), for Power BI read the text classes and verify after Fit to page | Any label that names an entity, unit or value is below the floor the design contract records (default 11 px/pt on desktop, 12 on a phone; axis ticks 10 on desktop, 11 on a phone); long labels wrap mid-token; metric size overwhelms context. Status chips and eyebrows at 11 px are not a trigger when the contract records that size |
| Density and grouping | Full-page rhythm, shared surfaces and open space | Every section has identical card chrome; key information competes with filler or repetition |
| Mobile priority | First mobile view and path to the main action | Desktop is merely stacked with no deferred section; an entity opened by an explicit tap is not in the first viewport and has no control to reach it that is visible and not covered by a fixed bar (top bar, bottom navigation, banner); important actions sit several screens down; narrow columns fragment labels |
| Detail continuity | Entity/detail view and return path | Detail looks like another product or loses selected context |
| Motion | Initial state, changed state, interruption and reduced motion | Effects lower the contrast of overlaid text or cross quantitative marks, delay data (values count up from zero on first paint or interpolate longer than about 600 ms), keep running while hidden, or leave an incorrect/stale state; a requested effect that meets these rules is Meets brief |

Apply relevant criteria only. Identical components can be intentional; a quiet enterprise design can satisfy a quiet brief. A pattern taken from the user's references or an approved design is not a revision trigger; judge it on readability and data truth, and raise Needs revision only where repetition hides the decision. Do not mark a specific aesthetic as universally wrong. For a premium request, record Meets brief / Needs revision / Untested with the specific artifact and visible reason. Keep this distinct from Pass/Fail checks on data and interaction. A row is Needs revision only for a Major finding (SKILL.md severities); a Minor finding keeps the row Meets brief and lists the correction. The visual conclusion is needs revision when any row is Needs revision, untested when a row the brief depends on is Untested, otherwise meets brief with the listed corrections.

Compare revisions using the same viewport, data and state. If the second revision preserves a rejected composition and adds only features or effects, return the work to art direction before adding more polish. Use concrete alternatives such as regrouping the analytical surface, changing comparison encoding or reprioritizing mobile; avoid feedback limited to "make it pop".

Keep verification bounded: landing view, one meaningful filtered state, detail and mobile priority view are usually sufficient. Screenshot evidence supports visual judgments only. Static geometry/contrast scripts cannot verify art direction, rendered type quality or subjective appeal. Do not claim that updated instructions alone guarantee a better future output.
